# 架构规则（2026-11-27 采用）

这份文档写给在本仓库里工作的人和 AI 代理。正文与具体 App 无关，可以直接用于同类的 Apple 多端 App（例如 Viozi）；Primuse 的具体路径、命令和数字放在附录 A。每条规则都带理由和检查办法，理由里的数字是 2026-11-26 至 27 日在 Primuse 上实测的。

状态：采用版，自 2026-11-27 起纳入版本管理，由架构关卡 `scripts/gate/gate.py` 在提交、推送和拉取请求时检查（见附录 A.3）。标「目标」的条目是方向，Primuse 尚未做到；其余条目现在就必须遵守。修改本文件要仓库所有者同意，并同步更新关卡的配置。

## 1. 分层

| 层 | 放什么 | 不放什么 | 怎么测 |
| --- | --- | --- | --- |
| 核心包（纯逻辑） | 模型、策略、算法、数据库表与查询 | 界面、单例服务、平台 UI 框架 | 包管理器直接跑单测，不经 App 构建和模拟器 |
| 服务层 | 有状态的服务对象：曲库、播放、音乐源、同步 | SwiftUI 视图 | App 测试；逻辑尽量下沉到核心包再测 |
| 界面层 | 各平台的视图与视图模型 | 数据库 SQL、整库计算 | 界面测试与真机清单 |
| App 壳 | 入口、生命周期、依赖组装、系统扩展点 | 业务逻辑 | 构建 |

规则：

1. 依赖只能向下：界面 → 服务 → 核心包。下层不引用上层的类型，包括写在 `#if os(...)` 分支里的引用。
2. 能脱离 App 测试的逻辑放进核心包。判断标准是「这段代码需不需要一个正在运行的服务对象才能给出答案」，不需要就下沉。
3. 多个平台共用的源码按目录共享，不逐个文件登记。新增文件不应需要改工程定义。
4. 层与层之间先用目录和依赖方向划界，不急着拆成独立模块。拆模块要先有测量证明值得：Primuse 实测把三端共用的服务代码（13 万行）抽成模块，需要公开约 3,450 个声明、60 个协议、补 38 个初始化方法、改约 620 个文件的导入，而这部分代码只占编译任务里类型检查时间的 13%。一个 60 万行的单模块里，改任何一个文件都要重新生成一次模块接口，每个平台各付一次。这一步实测 89% 是声明的类型检查，其中 57% 花在宏展开上（一次要做 24,348 次展开，`@State` 与 `@Observable` 各占一半），它不检查视图的 `body`。所以先减少宏展开（第 3 节，已把这一步从约 95 秒降到约 56 秒），拆模块排在后面，并且仍要先测量。

## 2. 数据归属与大集合

1. 一种数据只有一个事实来源。随用户数据量增长的集合（曲库、文件索引、补全状态、离线状态）以数据库表为准，内存里只留有界的窗口和缓存。
2. 不新建与集合同阶的内存结构：整库数组、整库字典、整库 id 集合都不行。整范围用行号列表或在主线程外流式遍历；物化成对象必须有上限。
3. 读数据走四种形状：按 id 取、按页取、计数、流式遍历。同步返回整个集合的接口不新增。
4. 数据库表的 SQL 只写在一个目录里，其他地方通过接口读写。
5. 这几条用静态检查守住，按棘轮执行：现有违规按文件记数，只许减少，新代码超出即失败。确有上界的例外在同一行写明上界和理由。
6. 规模预算写成测试：用确定性的合成数据（Primuse 是 10 万和 50 万条）断言常驻增长、峰值和关键查询耗时。预算常量集中在一个文件，调整要写理由。
7. 用户的小状态（喜欢、歌单、播放历史、评价）的落盘不依赖大集合是否在内存里。小状态的写入路径不读整库数组；要知道「某一行还在不在」就问数据库。
8. （目标）大集合的内存模型是可以放掉的缓存：启动时不装载，有人需要时装载，用完释放。走到这一步之前的每个提交都保持线上行为不变，新路径关着开关合入，用新旧两条路径的对照测试证明等价。

理由：内存 = 条数 × 每条成本 × 份数。Primuse 在 50 万首时曲库模型常驻 468 MiB；把模型放掉后归还 95–98%，说明常驻的就是这些集合本身。

## 3. 状态对象

1. `@Observable` 类的类体只放实例存储属性、指定初始化方法和 `deinit`。方法、计算属性、嵌套类型、类型别名和静态存储属性写在紧随其后的同文件扩展里。新写的类一开始就按这个形状写。
2. 扩展按职责分组；跨文件拆分时先保证同文件扩展已经到位，再考虑访问级别。
3. 一个状态对象只管一个领域。出现「什么都往里加」的类或文件（常量文件里塞策略类型、万行视图文件）时，按类型家族拆回各自的领域目录。

理由是实测：宏会对类体里的每个成员执行一次，每个用到该类的编译进程都要重做，约每成员 10 毫秒。Primuse 分两轮把 100 个类的成员移到同文件扩展（先是 13 个最大的类，再是其余类体不少于 25 个声明的 87 个类）：macOS 全新构建 514 秒 → 344 秒 → 306 秒，编译 CPU 时间 2,550 秒 → 1,327 秒，改一个文件后的增量构建从约 116 秒降到 71–74 秒，超过 1 秒的类型检查表达式全部消失。这是纯移动，移动的行逐字节不变。

检查办法：用语法树工具列出每个 `@Observable` 类的类体声明数，类体里出现方法或计算属性就迁移；工具的预演模式应当报告「没有可移动的」。

## 4. 就绪状态与破坏性操作

「查不到」不等于「没有」。数据还没装载、读取失败、目录落后，都会让查询返回空；把空当成「不存在」去清理，就是数据事故。

1. 任何会删除、清理、覆盖、上传或标记完成的代码，在用到数据的那一刻确认数据源已就绪，而不是只在入口确认一次。每次 `await` 之后都要重新确认。
2. 数据层自己的破坏性路径在未就绪时拒绝执行，不依赖调用方自觉。
3. 批量查询的返回值要能区分「此刻答不了」和「确实不在」。
4. 就绪之前收到的用户意图按目标值排队，不按「取反」排队。例如「喜欢」记成「设为喜欢」，重放时不会把已喜欢的取消。
5. 就绪之前收到的「读一行、改完写回」，在重放时才读，或者只排队改动的字段，不带着早先读到的整行覆盖回去。
6. 一个启动期才有的状态如果要在进程生命周期里再次出现（例如按需装载、空闲释放），先逐个核对只在启动时安全的消费者。
7. 清理任务需要一份「不许删」的名单时，名单答不出来就整步跳过，并且不把这一轮记成已完成，下次到期照常再试。

理由：Primuse 清查出十几处这类消费者，后果包括清空歌单成员、取消「保持下载」、把已喜欢的歌取消并同步到服务器、向云端上传空身份的记录。其中一处在线上就能触发：启动装载期间退到后台，定期清理会用空数组算出空的保护名单，把本地源的内嵌封面当成可删的。

## 5. 持久化与一致性

1. 两份存储之间的同步必须可追平：主存储每次写入在同一个事务里记变更流水，从存储落后时按流水只补改过的行。流水接不上（缺修订号、超量、内容对不上）时退回整库对账，不冒险。
2. 从存储落后期间，不从它回答任何「必须最新」的问题。这条不变量写在代码里检查的位置，并用测试钉住。
3. 迁移可续、可重入；旧数据在新数据校验通过之前不删。
4. 打开数据库不依赖 App 在前台或设备温度正常；只有整库规模的工作才受这类限制。
5. 新旧两条实现并存期间，用影子比对或差分测试证明两者答案相同，再切换。

理由是实测：没有流水时，从存储落后一个修订号要整库对账，10 万首 13 秒、50 万首 59 秒，期间不可读；加流水后 35 毫秒和 21 毫秒。

## 6. 工程与构建

1. 工程文件是生成产物。只改工程定义，再用生成工具重新生成；不手工登记文件。检查办法是把重新生成的结果与提交的工程按语义比较，差异必须为零。
2. 工程定义里优先写目录，不写单个文件。
3. 慢了先测量再动手。记录工具链、目标、缓存状态；用构建计时汇总看时间花在哪一类任务上，用类型检查告警找慢表达式。一个表达式在不同文件里耗时相同，通常是某个类型第一次被用到的固定开销，不是表达式本身慢。
4. 不靠改编译开关提速。实测去掉调试符号、改模块生成方式、跳过标准库拷贝都没有收益；加大编译批次约省 10%，但会让所有构建缓存失效一次。
5. 宏有编译成本，按展开次数算。生成模块接口时每次展开都要付一次，而且每个平台各付一次。新版 SDK 里 `@State` 也是宏（每个属性 5 次展开），所以视图文件里的状态属性数量同样计入这笔成本。怀疑宏是瓶颈时先数展开次数，再决定动哪里。
6. 验证构建的环境规矩见附录 A 第 4 节：同步时不保留修改时间；源码副本只在没有任务使用它时同步；一台机器同一时刻只跑一个构建。

## 7. 目录与命名

1. 源文件按领域分目录，测试目录与源目录镜像。根目录不堆文件。
2. 文件名说明内容，不带阶段、批次或负责人的后缀。
3. 同名文件不跨模块重复出现；一个目录名只表示一件事。
4. 不保留「名义上是常量，实际上什么都放」的文件。

## 8. 改动方式

1. 机械改动用工具做，并用脚本证明是纯移动：前后的行多重集合相同，移动的块连续且逐字节不变。纯移动和行为改动分开提交。
2. 删除之前先核实。每一项都在全仓库重新搜一遍（所有目标、测试、脚本、配置、按字符串引用的地方），并分三类：确认无引用、只剩测试引用、判断有误。只剩测试引用的类型要查清生产调用为什么消失：被有意替换的可以删，被重构误删的是回归，要报告而不是删。
3. 资源文件删除前确认原件另有出处。排除在打包之外不等于没有用。
4. 行为改动必须带测试，测试与代码同一个提交。
5. 新旧实现切换用差分或对照测试：同一输入分别走两条路径，比较结果。
6. 提交信息一行，说明对用户或对 App 改了什么；验证证据写进交接文档，不写进提交。

## 9. 验证关卡

提交之前必须通过的：

1. 静态检查（违规棘轮、工程文件校验、本地化键一致性）。
2. 核心包的测试：改了核心包就跑整个套件，否则跑受影响的套件。
3. 每个受影响平台的构建，包括测试目标。
4. 受影响区域的定向测试；阶段末尾跑一次整个测试包，与已知失败名单逐个比对，要求无新增、无消失。
5. 不能在构建机上验证的（真机内存、界面、无障碍、语音、签名相关的测试）列成清单交给人，并在报告里写明没有验证。

报告里区分三种说法：验证过、只读代码推断、没有做。

## 10. 多端交付

1. 改动共享代码时，逐个平台说明它得到了什么、没得到什么、为什么。编译通过不等于功能接入。
2. 平台专属的界面和会话各自验证。
3. 标题写某个平台的改动，如果触及共享文件，就要检查其他平台的行为变化。

## 11. 外部贡献

1. 逐个 PR 审查并给出结论表：每条发现一行，写明采纳、修正后采纳或不采纳。
2. 与已记录的需求或决定相反的改动不采纳。没有既定需求时比较两种处理，更合理的采纳。
3. 修正推到贡献者的 PR 分支，按 squash 合并，保留贡献者署名。
4. 多个 PR 互相冲突时，按依赖顺序排出每一步的完整状态，每一步都能编译再合并。

## 12. 多代理协作

1. 一个文件同一时刻只有一个修改者。并行工作分到不同的检出，按文件归属划界。
2. 执行代理不做 Git 写操作，由集成者审查后提交。
3. 每个里程碑写交接记录：改了什么、证据在哪、还有什么没做、下一步是什么。进度不依赖会话记忆。
4. 规格明确、有工具校验的机械任务交给较轻的模型；设计判断和有数据风险的核心改动留给最强的模型。
5. 代理的假设要用测量或实验验证后再当作结论。估算和实测在报告里分开写。

## 附录 A：Primuse 的对应物

### A.1 分层现状

- 核心包：`PrimuseKit/`（SwiftPM）。源文件在 `PrimuseKit/Sources/PrimuseKit/<领域>/`，测试在 `PrimuseKit/Tests/PrimuseKitTests/<领域>/`。
- 服务层与界面层目前在同一个 App 模块 `Primuse/` 里，iOS 与 macOS 共用。tvOS 目标编译 `PrimuseTV/` 加上 `project.yml` 里列出的一部分 `Primuse/` 路径。
- 模块抽取：事实调查见 `refactor-478/module-feasibility.md`。结论是现在不做。共用的服务代码（159 个文件、13.1 万行）在 tvOS 上只差 9 个外部符号就自成闭环，在 iOS 和 macOS 上差 46 个；抽取的代价见正文第 1 节规则 4，收益没有测量支持。
- App 模块的规模是 675 个 Swift 文件、约 61.3 万行（不含测试和核心包）。

### A.2 数据与内存

- 事实来源：`library-catalog.sqlite`，SQL 只写在 `PrimuseKit/Sources/PrimuseKit/Catalog/`。
- 棘轮：`scripts/check-crash-patterns.py`，基线 `scripts/library-scale-baseline.tsv`。
- 物化上限：`LibraryScale.maxMaterializedRows`（5,000）。
- 验收指标：50 万首合成库挂起不超过 100 MiB；真实状态挂起不超过 150 MiB、后台播放不超过 180 MiB；冷启动到可用不超过 1.5 秒。
- 路线与每一步的证据：`library-scale/P3-design.md` 第 7 节起，进度在 `library-scale/HANDOFF.md`。

| `baseline-integrity` | 第 2 节规则 5：基线只许收紧 | 错误 | 无 |
| `commit-message`、`tests-with-code` | 第 8 节规则 4、6 | 错误 | 无 |
| `toolbar-environment`、`widget-platforms`、`branding`、`localization-full` | 原有的 Ruby 与 shell 检查，有解释器和工具时才跑 | 错误（可选） | 无 |

- 钩子：`sh scripts/install-git-hooks.sh` 把本检出的 `core.hooksPath` 设为 `scripts/git-hooks`（pre-commit、commit-msg、pre-push）。钩子只读文件；被拦下时修代码，不用 `--no-verify`。
- 基线：现有违规按文件（`@Observable` 按类）记数，只许减少。命中变少后用 `--update-baseline` 收紧并随代码提交。放宽要仓库所有者在 main 上加 `--allow-growth "理由"`，理由以 `# 放宽：` 开头记在基线文件里；拉取请求里的放宽一律不通过。改名的大文件要同时运行 `--update-baseline` 让基线跟着改名。
- CI：`.github/workflows/architecture-gate.yml` 在拉取请求和推送 main 时运行，拉取请求用基准分支上的关卡代码查拉取请求的内容。仓库规则集 `scripts/gate/github-ruleset.json` 把检查 `architecture-gate` 设为合并前必需，管理员与 GitHub Actions 可以绕过。
- 跳过：缺工具的检查打印 `SKIPPED <规则>: <原因>`；本机不算失败，CI 用 `--require-all`，必需的规则跳过就算失败（可选的外部检查除外）。

### A.4 构建机规矩

- 构建机 16 GB 内存，同一时刻只跑一个构建。所有构建和测试都持共享锁：`lockf -k /Volumes/od/primuse-verify.noindex/verify.lock <命令>`，每一步带超时。
- 同步源码：`rsync -a --no-times --checksum --delete`。保留修改时间会让 Swift 的增量编译把内容变了的文件当成没变。
- 源码副本只在没有排队或运行中的任务使用它时同步。
- 等待脚本用不会自我匹配的模式，例如 `pgrep -f "b-run.s[h] <标签>"`；两个等待脚本用同一模式会互相卡死。
- macOS 的 App 测试在未签名的构建机上跑不起来，只能验证到编译链接。
